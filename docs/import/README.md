# Legacy import tool (`ledgertrack-import`)

Moves a legacy ledger (Bankman) into a running LedgerTrack. It talks to the HTTP API only. It has no database access and no dependency on server internals, so it can run from any machine that can reach the API.

```
go build -o ledgertrack-import ./cmd/ledgertrack-import
```

## What gets created

| Legacy | LedgerTrack | How |
|---|---|---|
| currency | product | `POST /products`, then `/activate` |
| merchant | client, type `corporate` | `POST /clients`, KYC submit (`legacy-import` verifier), verify, activate |
| merchant balance per currency | CBA account, wallet id `client-{client_number}-{product_code}` | `POST /accounts`, then `/activate` |
| opening balance | one transaction per account | `POST /transactions`, see below |
| lien / hold | wallet lien carrying the original reference | `POST /transactions` moving `available` to `lien` |

`client_number` is generated by the server (`CL-2026-123456`), so the wallet id is only known after the client exists. The tool reads it back from the API.

### Opening balances do not come from `system:control`

The account credit endpoint is hard-wired to `system:control:{ccy}`. Using it would put every migrated balance on the system control account and the trial balance would no longer match the legacy one. Instead each opening balance is posted through the native `POST /v2/ledgertrack/transactions` endpoint from a dedicated source, one per currency:

```
send [NGN/2 125000050] (
  source = @gl:migration:opening:NGN allowing unbounded overdraft
  destination = @users:client-CL-2026-123456-MERCH:wallets:NGN:available
)
```

The address is the wallet id without its `-{CCY}` suffix, the same one the wallet API and the account API use, so a migrated balance and a live operation are one account. The source account ends up with a debit equal to the sum of all imported balances of the currency. `verify` checks exactly that. The address follows the `gl:` convention and can be changed with `--source-template`. The tool does not depend on a GL registry; if the registry later requires `gl:migration:opening:{ccy}` to be registered, register it before `apply`.

Each lien is a second transaction `available -> lien` whose `reference` is the original legacy reference (so `GET .../transactions?reference=` finds it) and whose metadata carries `legacy_source_id`, `legacy_reference` and `legacy_created_at`. Liens are posted through the native endpoint rather than `/accounts/{id}/lien` on purpose: the account lien endpoint runs product validation (minimum balance, daily limits) and records the amount as daily debit usage, which would consume the merchants' daily limits on cutover day.

## Workflow

```
ledgertrack-import validate --input ./export --precision NGN=2 --precision USDT=6
ledgertrack-import plan     --input ./export --url https://staging.example --auth-token $TOKEN --state staging.json
ledgertrack-import apply    --input ./export --url https://staging.example --auth-token $TOKEN --state staging.json --yes
ledgertrack-import verify   --input ./export --url https://staging.example --auth-token $TOKEN --out reconciliation.csv --deep
ledgertrack-import status   --state staging.json
```

Use one `--state` file per environment. The file records the target URL and refuses to be used against another one.

| Command | Network | Writes | Purpose |
|---|---|---|---|
| `validate` | no | no | JSON schema per line, referential checks, amount checks, per-currency totals. Exit 1 on errors. |
| `plan` | yes | no | Compares the input with the server and prints create, update, skip, conflict and blocked per item. Exit 3 if there are conflicts. `--out plan.json` keeps the detail. |
| `apply` | yes | yes | Executes. Needs `--yes`. Safe to re-run at any time. Exit 1 if anything failed, conflicted or is blocked. |
| `verify` | yes | no | Reads every account back and writes the reconciliation CSV. Exit 1 on any difference. |
| `status` | no | no | Prints the progress and problems recorded in the state file. |

Global flags: `--url` (env `LEDGERTRACK_URL`), `--ledger` (default `ledgertrack`), `--auth-token` (env `LEDGERTRACK_AUTH_TOKEN`, sent as a bearer token, never logged), `--rate` (requests per second), `--concurrency` (default 4), `--timeout`, `--max-retries`, `--state`.

Other flags: `--trim-trailing-zeros`, `--allow-synthesized-kyc-evidence`, `--asset-template`, `--source-template`, `--adopt-unmarked-clients`, `--fail-fast`, `--deep`. They are described under the relevant sections below and in `--help`.

## Input format

JSON Lines: one UTF-8 file per entity type, one JSON object per line, blank lines ignored. Every line has a stable `source_id` from the legacy system. Unknown fields are rejected. The JSON schemas live in `internal/legacyimport/schema/` and are compiled into the tool:

* `products.schema.json`
* `clients.schema.json`
* `accounts.schema.json`
* `balances.schema.json`
* `liens.schema.json`

Sample files with fake data are in `docs/import/samples/`.

Amounts are decimal strings in major units: `"1250000.50"`. No numbers, no sign, no exponent, no thousands separators. More fractional digits than the currency precision are rejected, even `"10.500"` for a 2 decimal currency, unless you pass `--trim-trailing-zeros` and every excess digit is `0`. Conversion to minor units uses integer arithmetic only, with the precision from `GET /v2/ledgertrack/currencies`.

### products.jsonl (required)

| Field | Required | Notes |
|---|---|---|
| `source_id` | yes | Legacy currency id |
| `code` | yes | Product code, `[A-Za-z0-9_-]{1,64}`. Part of wallet ids and ledger addresses. To work with the wallet API (`/wallets/{walletID}/...`) the code must equal the currency (`NGN`) or end with `-{CCY}` (`RESERVE-USD`): the wallet API reads the currency from the end of the wallet id. `validate` warns otherwise |
| `name`, `category` | yes | |
| `currency` | yes | Must be enabled in the currency registry |
| `description` | no | The tool appends `[legacy_source_id=...]` because products have no metadata field |
| `precision` | no | Used by offline `validate`. Online commands use the server value and fail on a mismatch |
| `status` | no | `active` (default) or `retired`. Retired products are activated for the import and retired at the end |
| `rules`, `interest_config`, `fee_schedule` | no | Passed through. `rules.min_opening_balance` must be 0 because accounts are opened without a deposit |

### clients.jsonl (required)

| Field | Required | Notes |
|---|---|---|
| `source_id` | yes | Legacy merchant id |
| `legal_name`, `phone` | yes | LedgerTrack requires both for KYC |
| `kyc_level` | yes | 0 to 3 |
| `kyc_source` | yes | Free text saying where the level comes from. Stored in the KYC payload |
| `status` | no | `active` (default), `suspended`, `closed`, `pending` |
| `trading_name`, `registration_number`, `tax_id`, `incorporation_country`, `industry`, `email`, `address`, `legacy_created_at` | no | |
| `external_id` | no | The identifier callers use for the client in the legacy system (Bankman `clients.external_id`). Stored in the client's KYC payload as `legacy_external_id`, lower-cased, so the Bankman compatibility API can find the client. |
| `kyc_identifier` | no | Sent as `national_id_number`, which LedgerTrack requires from level 1. Defaults to `registration_number`, then `tax_id` |

Clients with accounts need `kyc_level >= 1` and a status other than `pending`. Two clients may not share legal name, phone and registration number (the tool relies on that to recover from crashes).

Levels 2 and 3 need documents and in-person or biometric evidence that a legacy export cannot provide. The tool refuses them unless you pass `--allow-synthesized-kyc-evidence`, in which case it submits placeholder documents and a placeholder biometric reference, all tagged `provider=legacy-import`. Decide with compliance whether that is acceptable.

### accounts.jsonl (required)

`source_id`, `client_source_id`, `product_code`, `legacy_account_number` are required. `status` is one of `pending`, `active` (default), `frozen` (active with debits frozen), `dormant`, `suspended`, `closed`. `opened_at` is optional. One account per client and product. A `closed` account must have a zero balance. LedgerTrack generates its own account number; the legacy one is stored in the account metadata.

### balances.jsonl (optional, at most one row per account)

`source_id`, `account_source_id`, `currency`, `amount`, `available`, `lien` are required. `amount` must equal `available + lien`, the currency must be the one of the account's product, and `lien` must equal the sum of that account's rows in `liens.jsonl`. `as_of` is optional and goes to the transaction metadata. A zero balance posts nothing. The opening transaction reference is `import:opening:{source_id}`.

### liens.jsonl (optional)

`source_id`, `account_source_id`, `reference`, `amount` (positive), `created_at` are required. `reference` is used verbatim as the transaction reference, so it must be unique across the ledger and must not start with `import:`.

## Idempotency, safety and resuming

* Every created object carries its `source_id`. Accounts and transactions have metadata (`legacy_source_id`). Clients have no metadata field, so the marker travels in the KYC payload, which LedgerTrack merges into `kyc_data`. Products are matched by their unique `code`.
* The server is the source of truth. Each run re-reads products, clients and accounts and re-checks every step before acting, so a lost or stale state file costs time, never correctness. The state file adds a checkpoint per item and the record that a non-idempotent create was started, which is what allows adopting an orphan after a crash.
* Transactions use deterministic references (`import:opening:{source_id}` and the original lien reference) and are also sent with `Idempotency-Key` equal to the reference. A repeat answers with the idempotency hit or a 409. On a 409 the tool fetches the existing transaction and compares source, destination, asset, amount and `legacy_source_id`. A match counts as already imported; a difference is reported as a conflict and nothing is overwritten.
* Retries with exponential backoff and jitter apply to reads, to 429, and to calls that are safe to repeat (state transitions that are no-ops when repeated, and transactions with a reference). Creating a product, client, KYC record or account is never resent blindly. After a timeout or 5xx the tool looks the object up first: by code for products, by wallet id for accounts, and for clients by the legacy marker or, for a client created just before the failure, by matching an unmarked `pending` client on legal name, phone and registration number (only if the state file shows that this run started the create).
* Order is fixed: products, clients (KYC and activation), accounts, opening balances, liens, then final statuses (account suspended, frozen, dormant or closed; client suspended or closed; product retired). The final statuses are skipped, and the result says so, while any earlier phase has a failure, because suspending a client early would block opening its remaining accounts.
* Statuses only move forward. If an object is already further along than the input (for example suspended after cutover) it is left alone.
* `--concurrency` bounds parallel requests and `--rate` bounds requests per second. All opening balances of a currency hit the same source account, so expect some 503 serialization answers under load; they are retried and are safe because of the deterministic references.
* `--adopt-unmarked-clients` is the recovery switch for a client that exists without marker, same legal name and registration number, still `pending` (for example after a crash with the state file deleted). Without it such a client is a conflict.
* Ctrl-C stops cleanly and flushes the state file. Re-run `apply` to resume. A lock prevents two processes from sharing a state file.

## Verification

`verify` reads every account and writes a CSV, one row per account and one row per currency:

| Column | Meaning |
|---|---|
| `row_type` | `account` or `currency_total` |
| `source_id` | account `source_id`, or the currency code |
| `remote_id`, `wallet_id` | server ids (accounts) |
| `expected_*` / `actual_*` | available, lien and total in major units |
| `migration_source_debit` | currency rows: debit on `gl:migration:opening:{ccy}` |
| `result` | `PASS` or `FAIL` |
| `note` | what differs, and status differences from the input |

Tolerance is zero: one minor unit of difference fails. The currency row passes only if the sum of the input, the sum of the imported accounts and the debit on the migration source account are all equal. `--deep` additionally checks that every opening and lien transaction exists with the expected postings. Account status differences are reported in `note` but do not fail the row, because statuses legitimately change after cutover. Exit code 1 on any failure.

## Amount scale

LedgerTrack's wallet and reporting code resolves the ledger asset with `currency.AssetFor`, which is `{CCY}/{registry precision}` (`NGN/2`, `USDT/6`, `JPY/0`), and scales amounts by the same precision. The tool follows that convention: the `--asset-template` default is `{CCY}/{PREC}`, where `{PREC}` is the precision the server reports for the currency, so imported balances are visible to balance, statement and finance report endpoints. A test pins the default against `currency.AssetFor`.

Ledgers imported with an earlier build of this tool that used `{CCY}/2` for every currency hold a different asset for any currency whose precision is not 2 (for example `USDT/2` instead of `USDT/6`). Re-import those on a clean ledger, or pass `--asset-template '{CCY}/2'` only when matching a server build that still hard-codes `/2`. Check this on staging before the real run.

## Limitations

* Clients and products have no metadata field, so their link to the legacy id is indirect (KYC payload and description marker) and is not unique-enforced by the server.
* The tool does not set ledger timestamps from legacy dates. Legacy times are stored in metadata (`legacy_created_at`, `legacy_as_of`). Back-dating would depend on server settings.
* Only the balance snapshot is imported, not transaction history.
* It runs as a single process per state file. Do not run two imports against the same environment at the same time.
* Individual clients are not supported. Every legacy merchant becomes a corporate client.
